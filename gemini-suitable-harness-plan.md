# Gemini Suitable Harness Plan

## Abstract Plan of what we want to achieve
1. Hyper-Optimized Human Interventions: Never present the human with a blank page or a raw, unexplained code diff. Every human touchpoint must be heavily pre-processed by the AI. The AI brings context, structured options, tradeoffs, and explicitly highlights non-obvious decisions. The human simply provides the verdict.
2. Leveraged Human Judgment (Owning the Outer Loop): The human's cognitive bandwidth is the most precious resource. The human should never do work that a model (even a fast/cheap one like Flash) can do. Reserve human energy strictly for high-agency tasks: defining intent (PRDs), exercising taste (Architecture/ADRs), and final accountability (Code Approval).
3. Cognitive Sustainability (Combating Review Fatigue): Because the AI can generate code faster than a human can traditionally read it, the harness must translate code output into human-digestible formats. Code reviews must include architectural summaries and risk reports so the human can maintain a mental model of the system without burning out.
4. Automated, Deterministic Back-Pressure: Subjective AI-on-AI review is secondary. The primary defense against AI hallucinations and shortcuts must be deterministic. We will heavily utilize executable scripts, linters, type-checkers, and automated tests to create objective boundaries the AI must pass before it even reaches the human.
5. Fail Fast and Escalate Elegantly: The AI should not spin in infinite loops burning tokens. Escalation triggers must be deterministic (e.g., attempt counts, wall-clock budget, token/cost cap, or a verification gate failing after N tries), rather than relying on the LLM's self-reported confidence. We enforce strict cost/token ceilings on the orchestrator and RSI loops to prevent runaway execution. When escalating, subagents must generate a standardized `escalation-report.md` artifact (detailing the goal, attempts, and the specific blocker). The Orchestrator simply delivers this report to the human, avoiding a lossy "game of telephone".
6. The agent alone will probably fail a lot of tasks and his creativity is fairly limited, so always give the agent guidance and knowledge for special topics that it acts as the human wants it to act
7. 100% of the code is written by the agent.
8. Use the agent not just for software development, we can also use it for researching stuff, improving the harness, thinking about new features, etc. The agent is a general purpose tool that can be used for many things, also unconventional usecases.

## The Harness (technical details)

### Agent Topology and State Isolation
- **The Orchestrator Pattern:** The harness utilizes a single Main Orchestrator Agent. This agent is an expert in the harness rules and manages the task backlog (GitHub issues). **Crucially, the Orchestrator knows almost nothing about the codebase.** It does not read code; it only routes tasks. Each subagent is responsible for pulling its own minimal, specific context (e.g., the `tdd-implementer` reads code files, while the `challenger` might only interact with the running app).
- **Subagent Routing & Communication:** Specialized subagents handle the actual labor. Crucially, only one subagent at a time is permitted to write code (the `tdd-implementer`), while all other subagents (like `reviewer` or `challenger`) evaluate its work and provide feedback.
- **Model Assignment:** We use Gemini 3.5 Flash for high-throughput, mechanical tasks (`tdd-implementer`, `cleanup`, `researcher`). For tasks requiring judgment, taste, or DoD enforcement, we route to a stronger model like Gemini 3.1 Pro or Gemini 3.5 Pro (`architect`, `reviewer`, `challenger`, `harness-builder`).
- **Sandboxed Execution:** Subagents operate in isolated environments (e.g., utilizing git worktrees) to experiment safely without affecting the main project state.
- **Single Point of Contact:** To prevent alert fatigue, only the Orchestrator Agent is permitted to ping the human, acting as the courier for reports generated by subagents.

### Human Interaction
- **The "Briefing" Principle:** Whenever the Orchestrator communicates with the human, it must do so as a concise "briefing." Messages must be dense, highly structured, and entirely free of conversational fluff.
- **Maintaining the Mental Model:** The agent's primary communication goal is to ensure the human never gets "lost." It must explicitly cite its reasoning, decisions, and memory sources so the human maintains a perfect mental model of the system's current state.

### Deterministic boundaries
- Rely heavily on objective checks: executable scripts, linters, type-checkers, and test suites act as the ultimate source of truth.
- The AI must pass these deterministic blockers before it is allowed to escalate to a human for a verdict.

### Skills
- **Architecture: Few Wide-Ranging Skills.** Instead of 100 narrow, highly-specific skills (which confuse the LLM's tool routing and create a maintenance nightmare), we will maintain a small set of robust, wide-ranging core workflows:
  1. `orchestrator`: The project manager and sole communicator with the human. Routes work to subagents.
  2. `researcher`: The asynchronous librarian. Scours the web for deep research (frameworks, best practices) and distills findings into dense markdown files in `.agents/memory/resources/`. This protects the main agent's context window from messy web search outputs.
  3. `architect`: Writes PRDs, ADRs, and implementation plans.
  4. `tdd-implementer`: The coder. Operates in isolated worktrees and follows strict deterministic boundaries.
  5. `reviewer`: Checks for code quality, DRY violations, and security flaws.
  6. `challenger`: The strict DoD enforcer. Adversarially checks for shortcuts and ensures the exact Definition of Done is met. For web/frontend tasks, it writes and executes ephemeral headless browser scripts (e.g., Playwright via the CLI) to programmatically click buttons and verify UI states, rather than relying on basic checklists.
  7. `cleanup`: Runs periodically when idle to fix tech debt, DRY violations, and formatting without altering business logic.
  8. `retrospective`: Analyzes runs and batches findings into GitHub Issues for human review.
  9. `harness-builder`: The meta-agent. Syncs with the human to review retrospective issues and update rules/skills.
  10. `skill-creator`: Used when generating new skills. I copied it from the anthropic skills repository.
- **Separation of Engine and Fuel:** The skills contain the workflow logic (the Engine) and orchestrate the steps, but they are agnostic to project-specific preferences. Preferences, rules, and domain expertise (the Fuel) are dynamically injected into them.

### Lean File Structure & Memory
- **Dynamic Semantic Exploration:** Instead of static routing tables (which bloat the prompt), the agent relies heavily on Semantic Search (`mgrep`). The `AGENTS.md` root file simply instructs the agent to dynamically search for relevant rules and resources before beginning a task.
- **The Flat, Un-Bureaucratic Structure:** The project strictly separates human-facing specifications from agent-only memory:
  1. `rules/` (Root): Strict, fluff-free constraints. Merges coding style, architecture, tool usage (e.g., `gh-cli-usage.md`), and LLM gotchas into one place.
  2. `specs/` (Root): The living truth of the software. Contains `templates/`, `prds/`, `adrs/`, and `plans/`. (Kept out of agent-only memory so humans can easily read and write them).
  3. `.agents/memory/resources/`: Deep context only pulled when explicitly needed via search. Contains PDFs, domain research, and `reference-repos.md` (which links to public GitHub repos for the agent to traverse using the `gh` CLI).
  4. `.agents/memory/rsi/`: The recursive self-improvement engine room. Stores run logs, human satisfaction scores, and synthesized lessons waiting to be verified and promoted to `rules/`.
- **Self-Healing Loop:** When the human provides feedback on an error, the agent uses a tool to record that lesson into the RSI folders or directly into `rules/`, ensuring the mistake is never repeated.

### Recursive Self Improvement
- **Post-Run Analysis:** Upon completion of a task or feature (e.g., triggered by a commit hook), the LLM automatically reviews the execution transcripts and generates a summarized retrospective report.
- **Human-in-the-Loop Judgement:** The human reviews this report to inject taste and intuition, identifying subtle bad patterns or architecture drift that the LLM is blind to.
- **Satisfaction Integration:** The human provides a "general satisfaction" assessment and high-level feedback. The harness then takes this human judgment, synthesizes it, and permanently writes the new lessons into the `Learned Experience` memory files.

### Technical Tooling Stack
- **Communication Layer:**
  - **Asynchronous (GitHub Issues & PRs):** The primary workflow for execution. The human assigns issues to the agent. The agent executes in a branch and opens a PR for human review. This treats the agent like a true remote team member and provides a perfect audit log.
  - **Synchronous (AGY IDE Chat):** Used exclusively for high-bandwidth alignment: drafting PRDs, architectural brainstorming, or "pair programming" through a severe blocker.
- **Actuation & Back-Pressure Layer:**
  - **GitHub CLI (`gh`):** The primary tool for the agent to interact with the project state, read issues, traverse external reference repos, and manage PRs.
  - **Lefthook & Biome:** The first line of deterministic defense. Git hooks prevent the agent from committing code that fails styling or basic linting, forcing immediate self-correction.
  - **Vitest & CI/CD:** The objective verifiers. The agent cannot declare a task done until tests pass locally and in the GitHub Actions pipeline.
- **Context & Memory Layer:**
  - **`mgrep` MCP:** The semantic search engine the agent uses to dynamically traverse the `.agents/memory/` folders without bloating its prompt (connected via a manual MCP bridge).
  - **Figma MCP:** Provides the agent with ground-truth design constraints to ensure UI implementation matches human taste.

## How to use the harness (The 3-Window Workflow)

The human experience is strictly divided into three separate contexts to prevent LLM prompt confusion. The human acts as the "Outer Loop" owner, while the agents execute the inner loops.

### 1. The Execution Factory (Window 1 - Semi-Autonomous)
- **Tool:** The `orchestrator` skill running in the main AGY window.
- **Workflow:** You start this agent when you sit at your computer (as the CLI runs locally). It runs a low-intensity polling loop (e.g., checking `gh issue list` every 5 minutes) when idle. Once it detects a new issue, it autonomously spawns `tdd-implementer`, `reviewer`, and `challenger` subagents to complete the work. It runs `cleanup` tasks if the backlog is empty. 
- **Human Touchpoint (Sync/Async):** It only pings you synchronously for a quick "Proceed?" or if it hits a deterministic blocker. Otherwise, it operates asynchronously, pushing PRs to GitHub.

### 2. The Planning Room (Window 2 - Synchronous)
- **Tool:** A separate AGY window using the `architect` or `researcher` skills.
- **Workflow:** You never plan features in Window 1. Here, you have high-bandwidth chats to draft PRDs, explore the codebase, or research new tools. The agent traverses public repos and helps you write ADRs. 
- **Human Touchpoint (Sync -> Async):** The final output of this synchronous collaboration is a bulletproof Implementation Plan. Once you approve the plan, a new GitHub Issue is created. Window 1's Orchestrator will pick it up asynchronously.

### 3. The Meta-Evolution Room (Window 3 - Synchronous)
- **Tool:** A separate AGY window using the `harness-builder` skill.
- **Workflow:** As Window 1 completes tasks, the `retrospective` subagent automatically batches its analysis and opens GitHub Issues detailing inefficiencies or hallucinations. Every few days, you open Window 3 to review these Retrospective Issues with the `harness-builder` agent. 
- **Human Touchpoint (Sync):** You discuss the failures, decide on new rules, and the agent permanently merges these new constraints into the `rules/` folder, ensuring the factory constantly improves.

## Step 1, Define Harness Skill, Rules, Memory, Create-Skill Skill...

Define this infrastructure that we can use it to build the rest of the harness.

### AGENTS.md
The root entrypoint. Instructs agents on the flat structure and mandates the use of semantic search (`mgrep`) to dynamically pull context.

### .agents/memory/HARNESS.md
This is the index file for the harness. It gets linked in the AGENTS.md file and lists all the skills, rules and memory files that are relevant for harness development. For each file it gives a link and a short explanation of what it is and when to use it.

### .agents/memory/resources/harness-engineering/reference-repos.md
This file contains a list of public GitHub repositories that are relevant for harness development. They should get traversed by the agent via the gh CLI, each repo should have a good description of what it is and what is interesting/relevant in there. In the `rules/gh-cli-usage.md` we will define how to traverse these repos.

### rules/gh-cli-usage.md
Rules defining exactly how the agent should traverse those reference repos and interact with GitHub safely.

### rules/harness-architecture.md
This file contains the rules and my preferences for the harness architecture. It should get already into the details on how it should be structured, how the agents should communicate, stuff to avoid, etc. It shouldn't be an implementation plan, but a set of rules.

### rules/rule-authoring.md
The "Definition of Done" for writing new rules. Enforces that rules are fluff-free, use RFC 2119 keywords (MUST, NEVER), are testable/deterministic, and are verified against duplicates via `mgrep`.

### .agents/skills/harness-builder
This skill is used to build the harness itself. Like any other skill, we don't define any rules in here, we just define how the agent should behave, we define the agent here, not the fuel (rule files).

It should define how the agent should work:
- **Context Enforcement:** It must proactively `mgrep` rules and memory files before acting, and continuously verify it has the full picture (combating LLM laziness).
- **Delegation:** For creating or editing *skills*, it must spawn a subagent using the `skill-creator` skill to prevent polluting its main context window. For deeper research, it must spawn a `researcher` subagent to avoid context pollution.
- **Rule Enforcement:** It acts as the sole author of the `rules/` directory. It must ensure rules are fluff-free, use strict modal verbs (MUST, NEVER), and do not contradict existing rules.

### .agents/skills/skill-creator
This file is already defined (copied from anthropic skills). It will be used always to create new skills.
